How it works

Roles

  • The human owns the project access, posts the request, and approves one labelled option in chat.
  • The maintainer agent reads the selected repo through a read-only GitHub connection, groups results by environment, and proposes options when a test fails.
  • Each volunteer runs the quickstart on their own machine and reports the command and result.
  • Switch holds the room, applies message-addressing rules, and delivers targeted messages between agents.

Flow

  1. The maintainer command creates a room and maintainer agent from a template. The setup script places the maintainer's OpenCode config in its workdir before any request is posted.
  2. Each volunteer joins from their own machine. The script places the volunteer config and clones this public repo before a session starts.
  3. The human pastes the printed request into the kickoff thread and @mentions the maintainer.
  4. Volunteers follow the numbered steps, then send each requested result to the maintainer with a targeted message and post it in the kickoff thread.
  5. Before waiting for a volunteer, the maintainer reads the thread context once in case the result is already there. It groups the results by environment and reads only the source files needed to explain a failure.
  6. If everyone passes, the maintainer posts a short all-pass report and doesn't ask for approval. If a step fails, it cites the source and offers labelled options with their tradeoffs and exact changes.
  7. The human approves one option in chat. The maintainer sends only that local change to the volunteers who need to rerun. It posts a final report in the thread. No agent changes the project repo.

Safety model

Volunteers use the root opencode.json from this repo. Bash is denied by default. These are the allowed patterns:

mkdir *
cd *
python3 *
cat *
ls
pwd
python3 --version
git clone *

OpenCode edits stay inside the volunteer workdir. Access to external directories and web fetching are denied. The setup script clones the public repo into that workdir before any session starts.

Cross-owner messages are blocked by default. A volunteer keeps its owner rule and gets one room-scoped exception for the maintainer agent and its linked messaging identity. In Solo, both agents share an owner and use owner-agents addressing.

The maintainer config denies OpenCode tools by default, then allows Switch tools and a narrow Bash rule for gh api repos/* with write flags denied. It reads project files only with GET requests like this:

gh api repos/{project_repo}/contents/<path> -H "Accept: application/vnd.github.raw"

The maintainer numbers the returned lines and cites full repo-relative paths. It doesn't clone or download source files, run other commands, start subagents, or write to GitHub or Google. Its workdir contains only opencode.json.

The human must approve a labelled option before the maintainer sends a fix. The fix stays in a volunteer workdir. The human applies any project change separately.

These guardrails aren't a sandbox for hostile code. Every allowed Python command can run arbitrary Python code. Review the quickstart before inviting volunteers and use a fresh workdir.

Local run results

These timings came from local runs. Greet6 had three owners and took 2m33s from request to final report. Greet5 took 3m09s from request to final report. Solo1 setup took 6.6s, and setup to final report took 5m03s.

In Greet6, bob used Python 3.9.6 and initially failed step 4. carol used Python 3.12.15 and passed. In Solo1, the judge used Python 3.9.6 and initially failed. The approved local change let the rerun pass.

Limitations

  • The three test environments ran on one Mac and differed by Python version.
  • No real Windows or Linux machine and no remote enrollment were tested.
  • The guardrails are not a sandbox.
  • Free model availability and limits can change.
  • Fixes are suggestions, not pull requests. A human applies any project change.
